# Code Review Checklist

## Flutter/Dart 代码审查清单

### 功能正确性
- [ ] 代码实现了期望的功能吗？
- [ ] 是否有足够的测试覆盖（unit/widget/integration）？
- [ ] 边界情况是否处理？（空值、空列表、网络错误）
- [ ] 错误状态是否有合适的 UI 反馈？

### 性能
- [ ] 是否存在不必要的 widget 重建？（缺少 `const`、过大的 widget 树）
- [ ] 是否在 UI 线程执行了耗时操作？（应使用 Isolate）
- [ ] 列表是否有适当的懒加载？（`ListView.builder` vs `ListView(children:)`）
- [ ] 图片是否使用了缓存和合适的尺寸？
- [ ] 是否使用了 `saveLayer()` 等昂贵操作？

### 代码质量
- [ ] 命名清晰？（变量、函数、类）
- [ ] 函数是否单一职责？
- [ ] 是否存在重复代码？（考虑提取为共享方法/widget）
- [ ] Dart 风格指南是否遵循？
- [ ] 魔术字符串是否提取为常量？
- [ ] 注释是否有必要？（说明"为什么"而非"什么"）

### 安全性
- [ ] API 密钥和 Token 是否硬编码？（应使用环境变量或安全存储）
- [ ] 用户输入是否验证和清洗？
- [ ] 敏感数据是否加密存储？
- [ ] 网络请求是否使用 HTTPS？
- [ ] 是否存在 SQL 注入风险？（字符串拼接查询）

### 可维护性
- [ ] 架构模式是否一致？
- [ ] 依赖方向是否正确？（UI → ViewModel → Repository → DataSource）
- [ ] 新代码是否容易扩展？
- [ ] 是否添加了必要的文档/注释？
- [ ] 导入是否组织清晰？

### 测试
- [ ] 单元测试覆盖了核心业务逻辑？
- [ ] Widget 测试覆盖了关键 UI 交互？
- [ ] 测试是否独立运行（无共享可变状态）？
- [ ] Mock 是否使用了正确的库？

## PR 审查流程
1. **理解上下文**：阅读 PR 描述，理解变更的目的
2. **大图审视**：先看文件变更概览，理解改动范围
3. **逐行审查**：从入口文件开始，跟随逻辑流
4. **运行代码**：如有疑问，本地拉取分支运行测试
5. **提供建设性反馈**：指出问题同时提供改进建议

## 反馈用语建议
- ✅ "这段逻辑可以提取到 ViewModel 中，减少 widget 的职责"
- ✅ "考虑使用 const 构造优化性能"
- ❌ "这段代码写得不好"（改为具体问题）
